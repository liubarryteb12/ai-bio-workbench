## 二、最重要的两个发现

### 2.1 出图代码没有参考参考库（第 7 项）

注册表 `figure_templates.json` 里 30 条 ready 模板**都登记了 source 指向参考库**，但 6 个真实出图脚本一处都没引用。溯源只是元数据关系，不是代码派生关系。

**已落地 `tools/dev/figure_source_provenance.mjs`**（第 11 道门禁）：要求每个出图脚本显式声明
`DERIVED / INSPIRED / INDEPENDENT`，并抓「声称派生却不引用库」的假溯源。
6 个脚本已按实测如实标注 `INDEPENDENT`。

### 2.2 L1 队列效应在代码层被量化（第 1/2 项）

`deg_limma` 新增 6 个诊断列，真机实测（DCM 58 vs Ctrl 12）：

| 指标 | 数值 |
|---|---|
| 单侧沉默（一组 >=95% 零） | 746 |
| 低检出（两组都 >=50% 零） | 17,234 |
| 队列可疑合计 | **17,982** |
| 显著基因 过滤前 -> 过滤后 | 3,649 -> **1,599**（剔除 56.2%） |

**超过一半的"显著基因"是队列伪影**，AUC=1.000 的来源被直接量化。

## 三、消融实验：诊断列的特异性（关键验证）

用 GSE316126（人 PBMC / NanoString / 三组严格平衡 12:12:12 / 同批次）做对照：

| 指标 | DCM 基准（跨队列） | GSE316126（干净） | 差距 |
|---|---|---|---|
| 队列可疑占比 | **41.7%** | **0.13%** | **约 320 倍** |
| 单侧沉默 | 746 | 0 | — |
| 低检出 | 17,234 | 0 | — |

**结论：诊断列不是过拟合噪声。** 干净数据几乎不误伤，跨队列数据准确抓出伪影。
因此剔除 56% 显著基因的动作是**真实去伪，不是误杀**。

## 五、新增的 3 道门禁（16 道总计）

1. **出图溯源诚实性**（第 11 道）：禁止假溯源，要求显式声明派生关系；
2. **母版解释器解析**（第 12 道）：要求 PATH 注入 + 可执行性校验，禁止改写调用行
   （改写会破坏桥接 bilingual 的行级计数，实测把 probe_env 误判成 bilingual）；
3. **出图规范合规**（第 13 道）：直读 PNG 的 pHYs 块判 300 DPI，不靠人眼。
   产线项目强制、历史项目只报告。

## 八、我犯的三处错误（记下来防复发）

1. **把 47 个母版批量改写 `python3` -> `$PY`**，破坏了 bridge bilingual 的行级计数，
   导致 14 条测试变红。回退三轮后改用 PATH 注入才对。
   教训：改母版的调用形态会牵动依赖「文本形态」的下游判定，必须先跑契约测试。

2. **把「最小边 >= 800px」当硬性判据**，把 1039x779 这种可读的图判成不合规。
   规范原文只规定字号 >=8pt 与 300 DPI，**并无像素下限**。
   教训：**把自己的推断冒充成规范**，比 bug 更危险，它会让测试错误地红，然后去修本来没问题的东西。

3. **用仓库根作参考库路径基准**，把 39/39 全部误判为缺源码。
   实际 `code_path` 是相对 `library/` 的。
   教训：解析相对路径前先确认基准，否则会得到一个「事实相反」的结论。
