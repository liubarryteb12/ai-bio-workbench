# cp -al 快照的体积台账口径（实测，2026-11-02）

## 结论

cp -al 在 K40 的 /opt 上是**真硬链接**，但"零开销"这个说法不成立。按正确口径记账，
一次快照的真实代价是**几十 MB 级**，不是 0，也不是 3.6G。

## 实测数据（/opt/R/4.5.3-site-library，f2fs，/dev/block/dm-40）

| 口径 | 数值 | 说明 |
|---|---|---|
| df 快照前后增量 | 131,872 KB（约 129MB） | 这是真实磁盘占用代价 |
| 分两次独立 du | 3.6G + 3.6G | **错误口径**，共享块被重复计入 |
| 单命令双路径 du | 3.6G + 15M | **正确口径**，第二行才是增量 |
| inode 抽样 | 751323 = 751323 | 硬链接成立 |

## 为什么分两次 du 会翻倍

du 在同一次调用生命周期内维护一张已访问 inode 哈希表来跳过重复硬链接。
分成两次独立调用时，第二次的哈希表是空的，于是把第一份的块整棵重算一遍。

## 为什么正确口径下仍有 15M，而不是 0

硬链接只共享**文件内容（数据块）**，不共享**目录项**。备份树要新建整套目录结构
和每个文件的 inode 与目录项，这部分元数据在 3.6G / 数万文件的规模上就是十几 MB。
df 的 129MB 增量大于 du 的 15M，差额来自 f2fs 的块分配粒度、目录索引与日志开销。

## 固化判据

验证 cp -al 快照是否成立，只看两项：

1. 抽样文件的 `stat -c %i` 相等（证明是硬链接而不是深拷贝）
2. 单次联合执行 `du -sh "${LIB}" "${LIB}.bak"` 的第二行**小于第一行的 5%**

第 2 条按比例判定而不是绝对阈值：Argon 给的"小于 5MB"在几十万文件的大库上会误报，
比例判据对大小库都成立。实测 15M / 3.6G = 0.4%，距 5% 有一个数量级的余量。

## 反例边界

在 /sdcard、/storage/emulated/0 等共享外部存储挂载点上，或跨挂载点（EXDEV）操作时，
硬链接不可用，cp -al 会退化为实拷贝。此时 df 增量会等于整库大小，判据 2 直接不成立，
这就是需要人工介入的信号。
