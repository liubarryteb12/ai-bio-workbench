# Gemini（Argon 模型）对 bioworkbench 稳态维护的建议（2026-11-16）

> 对话记录存于网页版 Gemini 会话「生信分析工作台稳态维护方案」。
> 提问背景已注明：纯 web 形态、不再向软件 App 方向迭代、单人维护、
> 目标为运行正常 + 功能够用 + 维护稳定灵活简单。

## Gemini 的开场判断

定位从「对外交付的软件商品」切换为「单人自用的稳态工具」后，
架构的核心矛盾从「防别人犯错 / 防合规风险」变成
「防自己心智负担过重 / 防 12GB ARM 硬件 OOM 与闪存写穿」。
商品级工程治理如果不做降维，维护测试和门禁的时间会超过真正跑生信数据的时间。

## 一、值得做的优化（按 ROI 从高到低）

1. **三线物理互斥锁与激进 GC（最高优，防 OOM 死机）**
   在 SQLite 租约层锁死全局并发度 = 1；每个算子 Stage 落盘后强制销毁
   Python 子进程，靠文件系统做进程间交接，彻底归还物理内存。

2. **依赖环境彻底冻结（防 ARM 编译地狱）**
   立即导出跑通环境的 lock 文件（conda-lock / requirements.lock / pnpm-lock.yaml），
   声明冰封期：除非新分析必须用新包，否则不执行 pip/conda update。

3. **重度算子切换 Backed / 磁盘映射模式**
   Line 2 / Line 3 的 AnnData 默认 backed='r' 或分块处理，
   中间矩阵落盘，用磁盘 I/O 换内存安全空间。

4. **UFS 闪存寿命保护与临时文件清道夫**
   纯临时日志与测试沙箱挂 tmpfs 或跑完即删；工单完结后一键归档
   （保留图件、DEG 表、manifest，自动删中间缓存矩阵）。

## 二、现有复杂度裁剪与降级（Gemini 的表格）

| 治理资产 | 裁剪动作 | 风险 | 保留底线 |
|---|---|---|---|
| 29 道串行门禁（含变异反证） | 砍掉日常串行执行，变异测试封存为「仅重构核心统计逻辑时手动触发」，改 6~8 道核心冒烟门禁 | 修改辅助代码时可能漏掉隐蔽边界退化 | 3 类硬门禁：manifest/JSON Schema 交接校验、黄金基线统计比对、fail-closed 数据完整性锁 |
| 2000+ 测试用例 | 冰封 85%（移入 archive_tests），只保留 < 200 个端到端数据流契约测试 | UI 边缘显示小 bug（自用一眼可见） | 三线各 1 个 mini 数据集黄金回归，能从头跑通出图即健康 |
| 报告脱敏契约测试 | 降级为导出时单函数过滤，不再作为流水线卡点 | 手动贴日志到公网可能带出路径或 key | .env 密钥隔离 + 「导出分享」时跑一次正则路径擦除 |
| 五类 JSONL 台账 | 5 合 2：run_manifest.jsonl（断点续跑 + 哈希溯源）+ error.jsonl | 失去细粒度审计流水 | 文件级断点续跑台账必须保留 |
| Pi CLI 双人工检查点 | 取消双检查点，保留六工具白名单，改全自动 + 事后 git diff 审阅 | Agent 跑偏改乱工作区 | 白名单与目录沙箱保留，跑前自动 git stash / 快照 |

## 三、日常维护最小例行

**定期三条（Gemini 建议写成 alias）**
- 开机/跑分析前 10 秒：存储余量 > 15GB、无 python/Rscript 孤儿进程、SQLite 无锁死。
- 每周/每大课题后 2 分钟：`PRAGMA integrity_check; VACUUM;`、清理结项工单中间矩阵、JSONL 轮转归档、git push。
- 每月 5 分钟：三条线 mini 黄金数据集端到端回归（替代 2000 个单测）。

**五个停手信号（出现即停止投递新工单）**
1. Swap 持续吃满 > 50% 或 dmesg 出现 oom 记录。
2. 同一工单断点重跑连续失败 2 次以上（非网络原因）。
3. 黄金基线统计数值（log2FC/padj）小数点后第 4 位漂移（种子失效或包被升级）。
4. 磁盘写入明显变慢或剩余存储 < 10GB（UFS 写放大）。
5. SQLite 频繁 SQLITE_BUSY 且无实际运行的子进程（租约释放死锁）。
