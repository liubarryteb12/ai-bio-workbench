结论
架构路线成立，但处于“高危悬空期”：两面物理隔离（PKG 契约桥接）+ 三层 AI 自主受控（C 方案检查点）在架构逻辑上完全自洽，守住了安全底线与吞吐效率的平衡。最可能翻车的点在于 D4.9 生产接线后的“状态撕裂与僵尸锁”——即 AI 的 dispatch_step 触发容器 OOM 或 ADB 闪断时，单权威租约与五态状态机之间的异常收敛闭环。
唯一施工优先级：D4.9 生产接线 → D2 同步接收器 → D0 桌面壳收尾 → D1 门户加固。
必须立即修正/补齐的 3 项架构决策：
推翻/修正“容器上限 7.5GB，单任务 8GB”的参数倒挂；
补齐 AI 自适应工具（propose_adaptation）的“最大重试预算与参数单调性约束”；
在 work_order/v2 与 receipt/v1 之间强制打通 adaptation_ledger（自适应变更台账）哈希链。
理由
为什么路线成立：
两面隔离 + PKG 传输：彻底切断了公网 Web 门户向内网管理端及 ADB 算力端渗透的攻击面。门户沦为纯粹的 Schema 校验器与打包器，控制台保持 Local-first 极简形态，符合单兵/小团队高可靠交付的工程直觉。
检查点 C 方案（180s 自动放行 + 签发永人工 + 降级走探索版）：解决了 AI 介入后的最大痛点——“既怕 AI 乱跑浪费算力，又怕步步卡点变成人工保姆”。立项 180s 宽限期给了人工干预窗口，超时自动放行保证了夜间/无人值守队列的连续吞吐；而将统计降级（EXPLORATORY_DEGRADED）分流到独立签名通道，既保住了核心交付物的学术严谨性（不污染标准版回执），又避免了生信真实数据因样本质量差而频繁陷入 failed/blocked 死胡同。
为什么优先级必须是 D4.9 → D2 → D0 → D1：
第一顺位 D4.9（生产接线）：当前 A1–A8 处于 fail-closed 的沙盒态，是整个系统最大的未验证架构假设。如果不先把新增的 3 个工具与真实生产执行器、单权威租约、授权打通，后面做出来的桌面壳（D0）展示的是假状态，同步接收器（D2）消费的是空包。必须最先引爆并排雷。
第二顺位 D2（同步接收器）：门户和 PKG 收件箱已就绪，sync 协议已实现但缺消费端。把 D2 接上，就能立刻跑通“PKG 入箱 → D2 拉取消费 → 转 work_order/v2 → D4.9 真实执行 → 产出 receipt/v1”的端到端无头（Headless）核心数据闭环。
第三顺位 D0（桌面壳收尾）：当 D4.9 和 D2 在 CLI/后台服务层跑通稳态后，Electron 桌面壳只需要做纯粹的 IPC 状态映射、180s 倒计时交互和人工签发 UI 绑定，避免一边调 UI 一边改底层状态机契约。
第四顺位 D1（门户加固）：门户填单已可用，且与内网通过 PKG 离线/准离线解耦，属于典型的边缘轻资产模块，任何时候加固都不影响主干流水线的死活。
风险（最可能翻车的 4 个命门）
参数倒挂引发的宿主机/容器级死锁（致命）：
硬事实第 4 条写明“容器上限 7.5GB，单任务 8GB”。如果单任务允许申请或实际触及 8GB，必然先击穿 7.5GB 的容器 VmRSS 防线或触发 Linux OOM Killer。在 proot/容器环境下，R/Python 子进程被 OOM 强杀极易导致父进程（执行器 wrapper）挂起或退出码丢失，进而导致 running 状态无法正常流转为 failed/blocked。
AI 自主调参的“合法死循环”与统计欺诈（高危）：
新增 propose_adaptation + run_validation + dispatch_step 后，AI 具备了“跑不通就改参数重跑”的闭环能力。如果没有硬性的重跑次数上限（Retry Budget）和参数退化底线（例如单细胞不断放宽 min.cells / nFeature_RNA，或 bulk 不断放宽过滤阈值直到强行凑出差异基因），AI 会在 running 态内部无限空转耗尽算力，或者产出一份形式上通过校验、实则毫无生物学意义的“合规垃圾”。
180 秒立项宽限期的“重入与竞态”（中危）：
在 Checkpoint #1 的 180 秒倒计时内，如果管理员在第 179 秒点击“拦截/修改”，而定时器恰好在第 180 秒触发 auto-pass 并调用 dispatch_step 获取租约，若缺少基于 CAS（Compare-And-Swap）版本号的原子状态跃迁锁，会导致工单被双重下发或状态机直接损坏。
ADB 单通道大文件回传与心跳抢占（中危）：
单细胞（RDS/h5ad）与空转交付物动辄数百 MB 到数 GB。在通过 ADB 10022 端口流式拉取（Streaming Pull）归档包时，高带宽占用可能导致控制面的租约续期（Lease Heartbeat）超时，引发工作台误判算力节点失联而强行吊销租约，造成“任务已算完、回传最后 1% 时被判死刑”的假失败。
下一步优先级（含架构修正裁定）
一、立即执行的 3 项架构修正（在动工 D4.9 前拍板）
修正内存水位红线（强制执行）：
将“单任务 8GB”徹底废除。确立三级严格递减水位：物理设备 12GB → 容器硬上限 7.5GB (mem_guard) → 单任务硬上限 6.5GB（R/Python 堆内存与多核 fork 预留 1GB 缓冲）。严禁任何单细胞/空转模块在 MulticoreParam/future 下开启大于 2 个 worker。
锁定 AI 自适应边界（写入 D4.9 接线规范）：
每个工单生命周期内，propose_adaptation 最多触发 2 次；超过即强制转入 blocked 交由人工裁决。
确立参数单调降级律：AI 只能向“更保守/探索版（触发 EXPLORATORY_DEGRADED 标记）”方向调整预设白名单参数，严禁篡改 work_order/v2 中的样本分组映射（GSM Mappings）、物种与主分析线类型。
固化自适应审计链（补齐契约）：
任何由 propose_adaptation 引发的参数偏离，必须生成不可篡改的 adaptation_trace 数组，不仅写入运行期 SQLite，还必须作为受保护字段写入最终的 receipt/v1.json 并纳入 Ed25519 签名范围。如果在立项后发生了未签名授权的参数漂移，第 28 道门禁直接一票否决。
