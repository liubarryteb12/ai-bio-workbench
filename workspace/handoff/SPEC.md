# SPEC v0.1 — 工作台工程骨架与远程链路打通（T1 阶段）

> 本规格只覆盖当前阶段：**打通本地到手机 Linux 算力面 + 建立工程规范与台账 + 搭框架**。
> 生信分析代码（R/Python 三条线）**不在本规格范围内**，属后续阶段。
> 状态：已按 user 要求分阶段推进，本文件随阶段演进而改版本号。

## Problem Statement

用户已有一套架构设想（云-端解耦：本地纯交互，计算存储下沉到手机 Linux 服务器，三条生信分析线物理隔离），
且在 `reference/` 下已有大量自备算力节点 服务器的实测经验（Termux + Ubuntu 容器 + adb forward + runit）。
但当前工作台本身还是空的：没有工程目录、没有台账、没有可复用的连接脚本、没有规范。
用户要求：**先打通链路 → 再立规范 → 再搭框架 → 再写分析代码**，稳步推进。

## Solution

建立一个持久化工程目录，内容分四层：

1. `con_hf/` 交接与台账（handoff、踩坑、操作流水、领域术语）
2. `ops/` 链路运维脚本（连接、自检、服务状态、文件传输），全部带退出码与可重复执行
3. `docs/` 工程规范与架构文档（目录规范、隔离约束、台账 JSON schema、Agent 读法）
4. `src/` 后续三条线分析代码的落点骨架（本阶段只建空目录与 README，不写分析逻辑）

三条线的物理隔离（`/mnt/ssd/bio_data/line1_bulk|line2_scrna|line3_spatial`）在目录规范中定义，
本阶段先验证 SSD 挂载状态，未挂载则明确记录为阻塞项。

## User Stories

### 链路（L）
1. 作为开发者，我想一条命令确认手机设备在 adb 在线，以便区分"设备没插"和"设备插了服务没起"。
2. 作为开发者，我想一条命令重建两条 adb forward（8022 / 10022），以便 USB 重插或手机重启后不用手敲。
3. 作为开发者，我想一条命令探测 Termux 底座 sshd 与 Ubuntu 容器 sshd 是否可连，以便在动手前确认链路。
4. 作为开发者，我想在 ssh 不通时看到"哪个环节断了"（adb / forward / sshd / 服务），以便按台账对应条目排查。
5. 作为开发者，我想链路自检脚本输出非零退出码表示失败，以便接入后续自动化。
6. 作为开发者，我想链路自检脚本幂等，以便反复跑不破坏现有 forward。
7. 作为开发者，我想看到四个 runit 服务（sshd/crond/ssh-agent/ubuntu-sshd）的pid与归属，以便判断是否被系统杀过。

### 工程规范与台账（D）
8. 作为开发者，我想有一份领域术语表定义"线1/线2/线3/DEG/DR genes/互不交叉"，以便所有文档用词一致不歧义。
9. 作为开发者，我想有一份目录规范定义服务器端三条线隔离结构与本地工程目录，以便新会话不用猜文件该放哪。
10. 作为开发者，我想有踩坑台账模板，以便新坑按"现象→根因→解决→备注"格式追加。
11. 作为开发者，我想有操作台账，以便每个会话的产出可追溯。
12. 作为开发者，我想有交接 handoff，以便跨会话恢复工作时不用重读整个对话。
13. 作为开发者，我想有任务台账 JSON schema，以便 Agent 后续能读状态做重试。
14. 作为开发者，我想台账记录里区分"实测过的"和"未验证的"，以便不把推测当事实。

### 框架（F）
15. 作为开发者，我想本地工程目录有清晰的 src/ops/docs/con_hf 分层，以便代码、运维、文档、交接分离。
16. 作为开发者，我想服务器端三条线目录结构在某处以规范形式固化，以便后续建目录有依据。
17. 作为开发者，我想知道外挂 SSD 当前是否挂载、路径是什么，以便判断数据面是否就绪。
18. 作为开发者，我想框架里的隔离约束可执行（脚本校验），以便"严禁跨线"不只是文档上的话。

## Implementation Decisions

- 工程根目录就是当前工作台根；`reference/` 是只读参考资料，**本次不修改其中任何文件**。
- 本地目录分层：`con_hf/`（交接台账）、`ops/`（运维脚本）、`docs/`（规范）、`src/`（后续分析代码）。
- 连接方式：沿用 `reference` 已验证的方案，不造新轮子。adb forward 8022→Termux sshd、10022→容器 sshd；
  SSH 别名复用 `~/.ssh/config` 里已有的 `k40` / `k40-ubuntu`。
- 连接自检脚本失败时输出必须指明失败环节，exit code 非 0。
- 系列脚本遵循用户机器习惯：PowerShell 写 PC 侧入口，bash 写手机/容器侧执行体；
  含中文的 .ps1 必须存 UTF-8 with BOM（避免 PowerShell 5.1 解析失败，reference 坑#86）。
- 台账 JSON schema 字段以 user 提供的草案为基线，`line_id` 枚举强制 `line1_bulk|line2_scrna|line3_spatial`。
- 本阶段**不安装**任何 R/Python 包，不改动手机侧环境配置。

## Testing Decisions

- 好测试的定义：**测外部行为，不测实现细节**。对运维脚本来说，即"跑完看退出码 + 看输出关键行"，
  不拆解脚本内部变量。
- 本阶段的验证手段：
  - `ops/` 下每个连接脚本必须实际跑过并留下输出（贴进操作台账）。
  - 链路验证用真实 `ssh` 调用（`echo` 探活 + 取 R/Python 版本），不用 mock。
  - 先例：`reference/RedmiK40_liunx_container/` 的 `e2e_ubuntu.R/py`、`pc-after-reboot.ps1`
    都是"真跑 + 输出进台账"的路子，本工程沿用。

## Out of Scope

- Web 前后端、可视化界面、AI 交互模块——更后续阶段。
