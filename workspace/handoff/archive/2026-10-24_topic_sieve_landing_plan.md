## 一、两种模式，本质不同（本轮核心划分）

用户明确指出：一个是让 AI 去调研，一个是已经调研好可以用了、输入/上传数据就行，本质是不一样的。
落地计划必须把它们当成两个独立模块建设，共用的只有筛子规则正本。

| 维度 | 模式 A：AI 自主调研 | 模式 B：客户已调研，录入/上传 |
|---|---|---|
| 客户给什么 | 一个研究方向（疾病名 + 兴趣点），或零散线索 | 已查好的数据集 / 填好的要素卡，或直接上传数据 |
| 谁去做 L0 到 L4 | **AI 外出调研**：GEO 检索、抓字段、填卡、打分、成链、反推课题 | 客户自己录要素卡（向导），或数据已定直接进执行 |
| 输出什么 | 课题候选清单 + 要素卡 + 数据筛选结论（一份调研报告） | B1：课题候选（录入版判定）；B2：分析结果（图 / 表 / 报告） |
| 界面入口 | 派给 AI 的一个调研任务，AI 按筛子跑完回报告，**没有表单** | B1 七步向导；B2 数据上传 + mod 选择（现有链路） |
| 筛子角色 | **完整 SOP**，AI 按 L0 到 L4 逐步执行并留痕 | B1 只做判定引擎；B2 只在准入做 L0 闸 |
| 依赖什么 | 网络（GEO / 文献）、AI 主动探索能力 | B1 纯本地判定；B2 算力面 + 现有 54 mod |
| 怎么测 | 端到端依赖外部数据源，按 SOP 逐步留痕 + 抽查 | B1 纯函数可测；B2 走现有 mod 测试 |

**关键澄清（防止又混成一件事）**：之前设计的七步向导属于**模式 B1**，即客户已经调研完、
把要素卡录进来让系统判定。它不是模式 A 的界面。模式 A 没有表单，它是一个 AI 任务：
客户给方向，AI 按筛子跑完 L0 到 L4，回一份带留痕的调研报告。

两模式的边界一句话：**模式 A 产出的是"做什么课题、用哪些数据"这个决策；
模式 B 产出的是"把已定的课题和数据跑出结果"。** 决策与执行分开，不互相冒充。

## 四、关键设计决定：语义级判定是加高，不是替换

用户裁定「采用 aims 内的准则，但其要改成语义级判定更优秀」。落地时**不能把现有正则拦截换掉**，
原因是物理性的：正则拦截跑在客户提交建项的那一刻，本地 JS、零延迟、不需要网络；
语义级判定要读筛子 L0 规则与边缘病对照表，做不到提交瞬间返回。

因此定为两道闸（模式 B1 与模式 B2 建项时都走）：

```
客户提交 / 建项
  → 第一道：词面快筛（现有 20 条正则，本地瞬时，命中即拒）        [已有，不改]
  → 第二道：语义级准入（筛子 L0 规则 + 边缘病三态）                [本计划新增]
  → 边缘病与机器裁不了的项 → 待人工裁定队列（8787）
```

第一道保留的另一个理由：`tests/aims_drift_guard.test.js` 断言 aims 清单写 20 条，
`tests/tumor_blacklist_parity.test.js` 判条数与同序，`portal/index.html` 有字面量副本。
替换会让这三处同时失效，属于扩张性破坏，与「复用既有 seam」相悖。

第二道只做增补：在 `aims.txt` §一.2 补语义级准入条文，`tumor_blacklist.js` 不改。

## 十、模式 A 三部分建设记录（2026-10-25）

用户把模式 A 明确切成三部分：调研需求填写 → 派发给 AI agent → agent 用调研工作流产出结果。
本轮建了第一和第三部分，第二部分走"主对话转派"的轻做法，未上子代理基础设施。

### 第一部分：需求填写页（已建）

| 项 | 位置 | 状态 |
|---|---|---|
| 需求单字段契约 | `con_hf/topic_survey/request_schema.json` | 六个字段，四必填两选填 |
| 需求页 | `portal/survey_request.html` | 三步向导，复用 portal 设计系统 |
| 接收端点 | `portal/serve.mjs` 的 `POST /api/survey/request` | 校验 + 词面快筛 + 落盘 |
| 落盘位置 | `portal/inbox/<ticket>.json` | ticket 形如 `TSV-20261025-xxxxxxxx` |

**关键设计**：本页只收"方向"，不收要素卡。要素卡的几十个字段由调研过程自己填。
这与模式 B1 的要素卡录入页是两回事，用户已确认。

### 第二部分：派发（轻做法，未建基础设施）

当前做法：需求单落在 `portal/inbox/`，由主对话读取后按 skill 执行。
没有自动化派发链路。理由见计划第二节：并排对话之间不能程序化互发，
子代理基础设施不在本期范围。

### 第三部分：结果选择页（已建）

| 项 | 位置 | 状态 |
|---|---|---|
| 结果页 | `portal/survey_result.html` | 五段渲染：准入、候选数据集、课题候选、待人工裁定、留痕 |
| 读取端点 | `GET /api/survey/result?ticket=` | 按 ticket 读，格式校验防穿越 |
| 选择端点 | `POST /api/survey/select` | 只回写 selection，不改调研结论 |

**待人工裁定三项**在结果页独立成段并标黄，客户不能自行勾选裁决，与既有裁定一致。
