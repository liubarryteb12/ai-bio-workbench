# SPEC v0.2 : BioanalysDesktop 本地交互层（T2 阶段）

> version 0.2 | 2026-10-12
> 本规格覆盖第二阶段：**把 BioanalysDesktop 做成可用的本地交互终端**。
> 三条线的分析代码仍不在本规格范围内（属后续阶段），但本阶段要打通"下发任务 → 看日志 → 看产物 → 看台账"的闭环。
> 术语一律用 `con_hf/CONTEXT.md`，不得另造同义词。

## Problem Statement

链路、规范、台账、三线骨架都已就位（T1 阶段完成），但日常操作仍要手动敲命令：

- 想看链路通不通、四服务活没活，要开终端跑 `pwsh -File ops/00_link_check.ps1`；
- 想跑一条线的某个步骤，要手写 R/Python 命令再 ssh 上去，日志散落在终端里；
- 想看某条线出了什么产物，要 ssh 上去 `ls -la` 一层层翻；
- 想确认台账合不合法，要跑 `ops/04_check_logs.ps1` 看文字输出。

用户是资深生信专家，不是运维工程师，不该被这些机械动作占注意力。
同时用户明确要求**云-端解耦**：本地只做交互、零算力，计算全部下沉到手机 Linux 服务器。
所以需要一个本地软件：把"状态总览、任务下发、日志回显、产物浏览、台账巡检"收进一个界面。

## Solution

在 `BioanalysDesktop/` 建一个 Vite + React + Node 后端的本地 Web 应用：

- **本地零算力**：前端只发请求，本地不执行任何 R/Python 计算。所有计算命令经后端 ssh 到 `k40-ubuntu` 执行。
- **后端复用既有链路**：不新造连接方式，直接用 `~/.ssh/config` 里已有的 `k40` / `k40-ubuntu` 别名，
  以 `child_process` 调 `ssh.exe` / `scp.exe`，与 `ops/` 系列脚本同源。
- **四个首版功能**（用户勾选）：
  1. 链路与算力总览：设备在线、forward 在位、两个 sshd 探活、四服务状态、磁盘与内存。
  2. 任务下发 + 日志流：选线、选步骤、填参数，提交后在服务器执行，实时回显 stdout/stderr。
  3. 数据面文件浏览：看三线 `raw_data/processed/results` 的文件树与大小，支持取回本地。
  4. 台账合规巡检：读 `system_logs/` 台账 JSON，标出跨线、写只读区、缺种子、`checkpoint_status=failed` 等非法项。
- **隔离约束进界面**：任务下发界面按线收敛可选步骤与路径，不允许在界面上构造跨线命令。
  后端对每条命令做行级 audit：拒绝含其他两条线 line_id 的命令。

## User Stories

### 链路与算力总览（M）

1. 作为用户，我想打开软件就看到手机设备是否在线，以便不用先开终端敲 adb。
2. 作为用户，我想看到两条 adb forward 是否在位，以便 USB 重插后知道要不要重建。
3. 作为用户，我想看到 Termux 底座与 Ubuntu 容器两个 sshd 是否可连，以便区分"链路断"和"服务没起"。
4. 作为用户，我想看到四个 runit 服务（sshd/crond/ssh-agent/ubuntu-sshd）的状态与 pid，以便判断是否被系统杀过。
5. 作为用户，我想看到 log 子服务是否 crash-loop（`down: log`），以便提前发现 #88 复发。
6. 作为用户，我想看到手机存储用量（Termux `/data` 与 SSD 数据面），以便判断空间是否要清理。
7. 作为用户，我想看到容器 CPU 核数与内存、当前负载，以便决定要不要把任务拆小。
8. 作为用户，我想一键重建缺失的 forward，以便不用手敲 adb 命令。
9. 作为用户，我想总览有一个"总体健康"结论（绿/黄/红），以便三秒内判断能不能开工。

### 任务下发与日志（T）

10. 作为用户，我想先选一条线（line1_bulk / line2_scrna / line3_spatial），以便界面只显示该线合法步骤。
11. 作为用户，我想在选定线后看到该线的步骤清单（来自 `src/<line>/README.md` 的步骤顺序），以便不靠记忆敲顺序。
12. 作为用户，想为某一步填参数（如 GEO  accession、样本分组、线程数、随机种子），以便同一脚本跑不同输入。
13. 作为用户，我想提交后看到命令的完整文本，以便确认下发的就是我想要的。
14. 作为用户，想像 tail -f 一样实时看到 stdout/stderr，以便任务跑一半就知道有没有报错。
15. 作为用户，想在任务跑的时候继续做别的（不阻塞界面），以便同时盯两条线。
16. 作为用户，想看到任务的退出码与结束时间，以便判断成功还是失败。
17. 作为用户，想任务失败时直接看到 stderr 末尾，以便不用翻完整日志。
18. 作为用户，想中止正在跑的任务，以便下错命令时能止损。
19. 作为用户，想每次下发自动写一条任务台账 JSON（含 line_id、step、seed、io_files、退出码），以便事后可追溯。
20. 作为用户，想界面在我下发跨线命令时直接拒绝并说明原因，以便隔离约束不只是文档上的话。
21. 作为用户，想看到当前有哪些任务在跑、排队情况，以便不重复下发同一步骤。

### 数据面文件浏览（F）

22. 作为用户，想按线浏览 `raw_data/processed/results` 的目录树，以便知道这条线现在有什么。
23. 作为用户，想看到文件大小与修改时间，以便判断哪一步的产物最新。
24. 作为用户，想把服务器的文件取回本地指定目录，以便本地做图或交付。
25. 作为用户，想在 `/mnt/ssd` 未挂载时看到明确提示而不是空目录，以便不会误以为"这条线没数据"。
26. 作为用户，想看到 `public_references/` 的内容，以便确认共享参考是否就位。

### 台账合规巡检（L）

27. 作为用户，想一键跑台账隔离校验并看到结果，以便不敲 `ops/04_check_logs.ps1`。
28. 作为用户，想看到每个非法台账的具体原因（跨线 / 写只读区 / 缺种子），以便定位去改。
29. 作为用户，想看到 `status=failed` 的最近任务及其 error_log，以便决定重跑还是先修数据。
30. 作为用户，想看到每条线的步骤完成度（哪些步骤有台账、最近一次何时成功），以便掌握三条线的进度。
31. 作为用户，想台账巡检结果能导出，以便贴进汇报。

## Implementation Decisions

- **软件根目录**：`BioanalysDesktop/`（用户指定）。原 `old_useless/` 残目录不动，等用户处置。
- **形态**：Vite + React + Node（Express 或 Fastify）单体应用，本地 `npm run dev` 起前后端，
  生产用 `npm run build` + `npm start`。不引入 Electron（当前无交付他人的需求，Web 形态开发快、零安装）。
- **本地零算力红线**：本地进程不得执行 R/Python 计算、不得下载生信数据、不得写 SSD。
  本地只允许：跑 ssh/scp、跑 `adb`（链路自检与 forward 重建）、读写软件自身配置。
- **后端到服务器的唯一通道**：复用 `~/.ssh/config` 的两个别名 `k40`（底座）与 `k40-ubuntu`（容器计算面）。
  底座只做文件传输与服务管理，计算命令一律走容器。后端不自己拼参数，全部经 ssh 子进程执行。
- **与 ops/ 脚本的关系**：软件是 `ops/` 的界面化，不是替代。底层能力优先调用同名脚本或等价命令，
  避免两套实现漂移。链路自检直接调 `ops/00_link_check.ps1` 解析其输出（单一事实来源）。
- **鉴权**：仅监听 `127.0.0.1`，不对外暴露。无登录环节（单机单人使用）；若端口冲突可换端口。
- **日志流实现**：后端用 `spawn('ssh', ...)` 拿 stdout/stderr 流，经 WebSocket 或 SSE 推给前端，不用轮询。
- **任务台账写入**：后端在任务结束后按 `docs/ledger-schema.md` 组 JSON，写到服务器 `system_logs/`。
  本地不存台账副本（避免两处漂移），界面从服务器读。
- **隔离约束的执行点**：
  - 前端：按线过滤步骤与路径选项，界面上无法构造跨线参数。
  - 后端：命令执行前做行级 audit，命令文本中出现其他线的 line_id 即拒绝执行并记原因。
  - 两处都拦，不依赖单点。
- **数据面未挂载的行为**：文件浏览与台账巡检读到"目录不存在"时，界面显示明确阻塞提示
  （"外挂 SSD 未挂载"），不得显示为空目录或假装成功。
- **配置落点**：软件自身配置（端口、默认日志目录、界面偏好）放 `BioanalysDesktop/data/config.json`，
  生信相关配置仍归各线 `envs/`，不混。

## Testing Decisions

- 好测试的定义：**测外部行为，不测实现细节**。对这个软件即"请求接口看响应、点界面看结果"，
  不拆解组件内部 state。
- 后端接口测试用 Node 内置 test runner（不引 Jest 等重框架），覆盖：
  - 链路总览接口在链路通时返回四段 PASS，在链路断时返回明确失败段；
  - 命令审计函数对含跨线 line_id 的输入返回拒绝；
  - 台账巡检接口对合法/跨线/缺种子三类样例给出正确判定（样例沿用 `cn_debug/samples/system_logs/`）；
  - 文件浏览接口对不存在的 `/mnt/ssd` 返回阻塞态而非空列表。
- 前端不做单元测试组件树，靠一条端到端人工验收清单（打开软件 → 四功能各点一次 → 记录结果进 `con_hf/操作台账.md`）。
- 遵循本工程既有路子：**真跑留证**，验证结果贴进操作台账，不用 mock 服务器。

## Out of Scope

- 三条线的分析代码（R/Python）：后续阶段，本规格只提供"下发与观测"能力。
- `/mnt/ssd` 挂载与 SSD 物理操作：需用户决策，软件只做检测与提示。
- 多用户、权限分级、远程访问：本地单人工具，不做。
- AI 对话式交互、自动生成分析方案：更后续阶段。
- 工作流引擎（Snakemake/Nextflow）集成：本阶段任务下发是"单步命令"，不是 DAG 编排。
- Electron 打包与分发：当前无需求。
